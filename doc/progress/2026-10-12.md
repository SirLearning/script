## 2026-10-12 — Watkins refchr VCF time estimate

- Question: extract all Watkins from `main_raw` pfiles, recode arms onto refchr (`chr1A`–`chr7D` plus Mit/Chl), then write one VCF.
- `--keep` is the measured ~6 h / ~0.9 TB pgen+pvar step. Refchr is `--update-chr` / `--update-map` plus an arm merge, a second pgen rewrite of a few hours, not a new alignment.
- One multi-sample VCF of the ~2.9e9 pfile variants and 2795 samples is about 32 TB uncompressed. Export is on the order of 1–4 days and is the slow step. Per-sample VCF split remains the 372-day path.
- That 32 TB is all chromosomes together, hard GT from the pgen. Per-sample AD/GL are only in the source VCF. One VCF per refchr chromosome (two arms merged) is the same bytes split into 24 files. Keeping GT:AD:GL raises the all-chromosome total to roughly 200 TB and requires reading the 24 TB VCF.
- `plink2 --export vcf` from the Watkins chr044 pgen keeps pvar INFO. Site 44-21 INFO matches the source VCF; FORMAT is GT only (`0/0` versus `0/0:150,0:2,47,285`). INFO/NZ and INFO/AC stay the full-cohort counts after `--keep`.
- Dropping INFO with `pvar-cols=xheader` and running `bcftools +fill-tags -t AC,AN,AF,MAF,NS` rewrites site 44-21 as `NS=2783;AN=5566;AF=0;MAF=0;AC=0`. DP and allelic depth stay unavailable.
- Direct `bcftools view -S` from the source VCF is slower than `plink2 --keep` plus `--export`. Both paths write the same GT VCF; bcftools must rescan the 24 TB `GT:AD:GL` VCF, while `--keep` reads the 1.77 TB pgen in about 6 h. bcftools cannot read pgen.
- Keeping AD/GL, `bcftools view -S` of all 2795 Watkins on chr036 wrote 512 MiB uncompressed in 31 s (113% CPU, about 3.4 MB/s of the compressed input, FORMAT still `GT:AD:GL`). Scaled to 24.42 TB that is about 83 days serial. chr001 (838 GB) is about 2.8 days and sets the wall time if chromosomes run in parallel.
- That `view -S` copies site INFO unchanged. The gap versus pgen is the 24 TB text `GT:AD:GL` scan, not an INFO recalculation.
- `bcftools view --threads 8` on the same chr036 slice was 28 s versus 31 s without threads (155% CPU). The VCF files have no tabix index. Parallelism that matters is one process per chromosome: 192 cores, wall time set by chr001 at about 3 days.
- Arm-parallel `view -S` still leaves refchr possible. The plink2 `--update-chr` / `--update-map` path drops AD/GL. The same arm-to-`chr1A` rename and second-arm `POS + ref_start` can run in the extract stream, then the two arms are concatenated.
