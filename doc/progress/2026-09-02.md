**Phenotype source.** New `src/python/genetics/phenotype/trial_source.py` turns the DBone
export (`wap_z18_z20_p_plant_height_phenotype.csv`, 5900 plot rows) into project sources
under the new resource folder `00data/13phenotype/`. Two things had to be worked out from
the data rather than assumed:

- Genotype IIDs come in two shapes, `P0001` and `P0030A`. The numeric ranges do not
  overlap, so stripping a trailing `A` is an unambiguous join key. All 2000 phenotyped
  accessions then match `assoc.keep` with nothing left over.
- Jimai22 sits in 83 fixed plot slots. Only the 2019 rows carry the `-Jimai22` label;
  the same slots in 2018 and 2020 are unlabelled, and those 83 ids are exactly the ones
  with no WAP genotype. All three years of those slots go to the check source, so
  check-cultivar measurements never enter the association panel.

Outputs: `wap_plant_height.plot.tsv` (tidy, 50094 values), `wap_plant_height.pheno.tsv`
(wide per-year and overall replicate means), `jimai22_plant_height.plot.tsv` (2236 check

repeatable even though year means differ (93.8 / 113.5 / 111.0 cm). Replicate means are a
plain average — no BLUE/BLUP, no spatial or block model.

**Tracks run.** `phenotype_wap` (mod `wap_ph`), `cohort_freq` (mod `test_wap_refchr`, 8/8),

**Bugs found and fixed** — all four were invisible to the earlier `-preview` check, which
stopped at the parameter guards before reaching any of this code:

- `partial_cohort_freq` / `partial_assoc_wap` did `pfile + [...]` on the immutable
  `ArrayTuple` returned by `listMergedSubgenomeTestPfileTuples`, throwing
  `UnsupportedOperationException`. Now spread into a fresh list.
- `partial_assoc_wap` resolved `assets/NO_COVAR` from `projectDir`, which points at the
  entry script's folder when `partial_router.nf` is launched directly. Now `moduleDir`.
- `wap_matrix` wrote missing phenotypes as empty fields. PLINK2 splits on whitespace,
  collapses them, and rejects the row as short. `save_df_to_tsv` gained an `na_rep`

unanchored `Others` pfile (3 variants survive MAF plus LD pruning, `--pca approx` needs

`plot_gwas_results` drew "Manhattan-like" scatter of P-sorted variant index against
-log10(P), which is a decay curve, not a Manhattan. Added a generic

## 2026-09-02 — SUPP — annotate_vep and variant_sets on test_wap_refchr

Closing the other half of the chain. Both tracks now derive their inputs from a mod's
publish tree instead of taking one hand-picked file, which is what turns them from pilot
scripts into pipeline steps.

**Coordinate finding that unblocked VEP.** `test_wap_refchr` looked unannotatable at first:
its `#CHROM`/`POS` are linear whole-chromosome coordinates (chrom 1 running to 594 Mb),
while `wheat_v1.1_Lulab.gff3` and `abd_iwgscV1.fa.gz` use split segments (chrom 1 stops at
471 Mb). The recode had left the variant **ID** untouched, though: ID `2-56199649` on CHROM
1 POS 527503654 is exactly `471304005 + 56199649`. So the ID column is already in GFF
coordinates. New `pvar_sites_vcf` builds the VEP input by parsing the ID; no lift-over or
mapping table is involved. Verified 0 non-conforming IDs across the A pvar.

**annotate_vep.** `--vep_from_mod` builds one sites VCF per merged subgenome, then runs VEP
in Conda `anno`. A, B and D finished together in 13m34s (18.9 CPU hours) over 8.5M variants.
Consequence proportions look right — in the first 2M A rows, 13069 missense and 178
stop_gained against 1.81M intergenic.

Three failures on the way, all real:

- `--offline` makes VEP demand an Ensembl cache directory, which does not exist for wheat.
  `--gff` plus `--fasta` is already an offline run, so the flag was simply wrong.
- The BGZF FASTA needs its `.fai` and `.gzi` staged alongside it, not just the `.gz`.
- `Others` aborted on "Cannot get chromosome from VariationFeature". Two separate causes:
  segments 43 and 44 (the organelles) are absent from the GFF, and segment 0 hits
  `throw(...) unless $chr` in `AnnotationSource.pm:241` — Perl reads the string `"0"` as
  false. The organelle variants are now dropped with a count in the log, and segment 0 is
  renamed to `chrUn` in both the GFF and the sites VCF, which recovers all 116572 unplaced
  variants against the 29863 GFF features that live there.

Added `--vep_subgenomes` so one subgenome can be redone without recomputing hours of
annotation for the others.

**variant_sets.** `--variant_sets_from_mod` discovers `{id}.vep.tsv` plus the
`{id}.{wgs_core,assoc}.afreq` pair per subgenome and fans coding_mask, dual_af and the set
build out across them. `coding_mask_from_vep`, `dual_af_from_afreq` and `variant_sets_build`
took separate `path`/`val` inputs and wrote fixed log names, which collide once four tasks
run at once; all three now take a `tuple val(prefix), ...` and name their logs after the
prefix. `run_coding_mask` also read the VEP table with the generic loader, which took the
first `##` metadata line as the header — added `load_vep_tab_table`, with a test.

Per-subgenome sets (A / B / D / Others): pLoF rare 292 / 324 / 284 / 2, pLoF common in WAP
16 / 20 / 10 / 0, protein-altering rare 12991 / 13270 / 13169 / 3. Two numbers are expected
artefacts rather than results: `n_plof_rare_wgs` equals `n_plof_rare_wap` exactly because
the two cohorts are the same samples on a WAP-only mod, and `mis_consensus` / `mis_severe`
are zero because a GFF-only VEP run has no SIFT or PolyPhen.
