## 2026-09-03 — Wire the epigenome BEDs and the TPM atlases into the pipeline

Two resource folders had been staged under `00data` without a consumer:
`11epi_anno` (21 per-base conservation/epigenome BEDs, ~220 GB) and `12cs_tpm`
(two gene expression atlases). Both are now real pipeline tracks —
`partial_task site_anno` and `partial_task gene_expr` — and both feed optional
inputs into `variant_sets`.

### The degeneracy encoding is the inverse of the obvious reading

The featHighRes README lists `degeneration` as taking 0, 1 or 2 and says nothing
about what the codes mean. Guessing here would have been expensive, so I derived
codon positions from the prepared VEP GFF, pulled the actual codons out of
`abd_iwgscV1.fa.gz`, computed fold degeneracy from the genetic code, and
cross-tabulated 271k chr1A CDS bases:

| true fold | degen=0 | degen=1 | degen=2 |
|---|---|---|---|
| 0-fold | 2563 | 0 | 172426 |
| 2-fold | 49437 | 10 | 11 |
| 3-fold | 4722 | 1 | 0 |
| 4-fold | 629 | 41512 | 0 |

So **2 is non-degenerate and 1 is 4-fold**, not the other way round. Taking the
intuitive reading would have built the "neutral" reference set out of 0-fold
sites — the most constrained positions in the genome — and quietly inverted
every downstream comparison. The mapping and this table are recorded in
`site_anno.py` and in `domain/ref_v1_resources.yaml`.

### site_anno

`00data/11epi_anno/chr1A_featHighRes.bed.gz` ends at 594,102,056, which is
exactly the two-arm total in `infra/wheat/ref_v1.py` (471,304,005 + 122,798,051).
That makes these files **refchr_linear**, the same system as the `*_refchr`
`#CHROM`/`POS` — so unlike `annotate_vep`, which has to parse segment
coordinates out of the variant ID, this join is a plain `(CHROM, POS)` match.

Three properties that shaped the implementation:

- The files are **not** contiguous per base. Line 58510 of chr1A lands at
  position 64062; unannotated positions are simply absent. So line number is not
  position and the join has to be interval-based, with variants in the gaps
  getting NA.
- There is no tabix index. Building 21 of them and then doing ~8.5M random seeks
  costs more than one sorted pass, so `site_anno_extract` streams each BED once
  through `bgzip -dc | mawk`, holding that chromosome's wanted positions in a
  hash. One pass runs about an hour per chromosome; with `maxForks 8` the whole
  genome is three waves.
- Only chr1A–chr7D exist, so subgenome `Others` (chrUn, Mit, Chl) has no source
  and is skipped with a warning rather than failing.

`SIFT`, `PPH2` and `LIST2` are present but populated on only 0.1–0.6% of CDS
bases, so they do **not** close the gap left by a GFF-only VEP run. The dense and
genuinely useful columns are the conservation stack (phyloP and phastCons across
three clades, GERP, four CE flags) and the chromatin tracks.

### gene_expr

The two atlases disagree on gene ID version: `camp/` is already v1.1 (`…02G…`)
while `ramirez2018_refseq1/` is v1.0 (`…01G…`). The v1.1 GFF turns out to carry
`previous_id=` on every gene row, which is the official map, so no string
surgery is needed. Measured against the GFF: camp joins 105,200 / 105,200 and
ramirez covers 104,200 of the 107,891 v1.1 genes.

The trap here is the `LC` suffix. HC and LC genes are numbered **independently**
in v1.0, so `TraesCS1A01G000100` and `TraesCS1A01G000100LC` are different genes
and "normalizing" by stripping the suffix silently merges them — sorting the
269,583 ramirez IDs after a naive strip collapses them to 158,793. The GFF is
HC-only, so LC genes are dropped instead, with the count reported.

Run outcome on the ramirez atlas: 269,583 input genes, 104,200 mapped, 158,793
LC dropped, 88,590 expressed at TPM ≥ 0.5, median peak TPM 8.6, median tau 0.65,
28,332 genes tissue-specific (tau ≥ 0.85) across grain / leaves-shoots / roots /
spike. Ran in 2m53s.

### variant_sets now takes both

`VariantSetSpec` gained `site_flags`, `site_not_flags`, `degeneracy` and
`require_expressed`, and an empty `masks` tuple now means "do not constrain the
coding mask", which the non-coding sets need. Five new sets activate when the
extra tables are joined: `neutral_4fold`, `conserved_noncoding_rare_wap`,
`regulatory_rare_wap`, `plof_conserved_rare_wap`, `plof_expressed_rare_wap`.

`neutral_4fold` is the point of the exercise: the MAF spectrum and Tajima's D
work has had no within-genome neutral baseline, and 4-fold degenerate,
non-conserved sites are that baseline.

## 2026-09-03 — Name the ref-chr chromosomes instead of reusing the first arm id

- Question from the session: why does the plant-height Manhattan still say
  `1 7 13 19 25 31 37` when `test_wap_refchr` is supposed to be arm-merged?
- Diagnosis: the merge was real but only half-named. `write_all_ref_merge_update_maps`
  recoded both arms onto `ref_merge_chr_id()`, which returned the *first arm's*
  numeric id, so chr2A was labelled `7`. POS was genuinely whole-chromosome linear —
  chr2A reaches 780,797,860 against a part1 length of 462,376,173 — and every pvar
  carried exactly 7 odd-numbered codes per subgenome, which is what a completed
  merge looks like. Only the label was legacy.
- Key fact that made a clean fix possible: the variant `ID` column is **not** touched
  by the recode. It stays `{original arm}-{local pos on that arm}`, e.g. a chr2A
  part2 variant sits at `#CHROM chr2A / POS 462376691` with `ID 8-518`. Every
  annotation table (VEP, coding_mask, dual_af, site_anno, variant_sets) joins on ID,
  so renaming `#CHROM` invalidates none of them.
- `ref_merge_chr_id` → `ref_merge_chr_label`, now returning `chr2A` / `chrUn` /
  `Mit` / `Chl`. Because a first arm is no longer an identity row, the update maps
  now carry every variant, not just second arms; POS is unchanged for first arms
  and organelles. A second pass over an already-named pvar emits nothing, so the
  recode is now detectably idempotent, which it was not before.
- `load_pvar_ref_variants` accepts all three codings on disk: arm-numbered source
  pfiles, legacy first-arm-coded merged pfiles, and name-coded merged pfiles. Added
  `plink_chr_tokens_for_ref_chrom` so the `--chr` token lists written next to focal
  samples are right for either merged coding.
- Correction worth recording: an intermediate version of this change rejected
  arm-numbered pvars whose POS exceeded the arm length, on the theory that
  re-offsetting them would corrupt POS. That was wrong and would have broken every
  existing `_refchr` pfile. A first arm has `ref_start` 0 in `_POSITION_FILE_S`, so
  `plink_segment_to_ref_position` is the identity there and the legacy coding always
  read correctly. The guard was removed and a test now pins that behaviour.
- `site_anno_extract` matches the pvar on either the numeric arm id or the
  chromosome name, so `test_common_inter_refchr` (still numeric) keeps working.
- Audited plink invocations: everything on the ref-chr path already passes
  `--allow-extra-chr`, so string chromosome codes need no new flags. `load_plink2_glm`
  never casts CHR to int, so the Manhattan picks up the names with no plot change.
- New entry `subworkflows/tmp/refchr_rename.nf`: rename only, no rebuild. Rebuilding
  was rejected because `test_wap_common_refchr` and `test_wap_thin_refchr` are random
  subsamples and a rebuild would draw a different variant set, invalidating their
  published LD results.
- Ran it over the three WAP mods (exit 0). Verification: variant counts identical per
  subgenome; max POS per chromosome identical to the pre-rename capture (chr1A
  594,098,545 … chr7A 736,695,076); IDs preserved (`8-518` still present); and both

- Tests: `tests/test_ld_along_chr.py` 21 passed; whole suite 210 passed in 108 s

## 2026-09-03 — SUPP — ref-chr rename audit follow-up

An audit pass over every reader of pfile `#CHROM` turned up three call sites the
rename work had missed. All are reachable only on the renamed `*_refchr` mods, so
they were invisible in the GWAS rerun.

- **Silent zero counts (worst of the three).** `summarize_chr_variant_counts` in
  `plink/results_io.py` builds its per-chromosome table by walking
  `all_ref_v1_plink_chr_ids()` and doing `counter.get(str(plink_chr), 0)`. Once the
  pvar carries `chr1A`-style labels the counter keys never match, so every row —
  and the total — reports 0 without raising. `--partial_task chr_counts --mod
  test_wap_refchr` would have produced a plausible-looking, entirely empty table.
- **Crash on named chroms.** `iter_process_pvar_positions` (same module) casts
  `int(parts[0])`, which raises on `chr3A`. Feeds `compute_genome_bin_counts`.
- **Would-be wrong join.** `annotate_variants_popdep_from_pvar` (`variant/popdep.py`)
  and its MQ twin (`variant/mq.py`) also cast `int(parts[0])`.

Fixes:

- Added `pvar_chrom_to_plink_chr_id` to `infra/wheat/ref_v1.py` — one shared
  normaliser mapping an arm number through unchanged and resolving a merged name to
  its first arm (`chr3A` → `13`, `chrUn` → `0`, `Mit` → `43`). This reproduces the
  row layout the numeric `_refchr` pfiles already produced, so `chr_counts` output is
  comparable across the rename.
- `results_io.py` now normalises through that helper in both `_count_variants_in_pvar`
  and `iter_process_pvar_positions`. Binning stays correct because merged variants sit
  on a first arm, where `plink_segment_to_ref_position` is the identity.
- popdep/MQ deliberately **do not** normalise. They join arm-local positions against
  frozen per-segment depth grids, so folding `chr3A` onto segment 13 would silently
  mis-key every second-arm variant. Both now raise a `ValueError` naming the offending
  `#CHROM` and pointing at the arm-numbered source pfile. Current wiring only ever
  annotates the pre-recode pfile, so this is a guard rather than a behaviour change.
- New `tests/test_results_io_refchr.py`: asserts the named pvar yields counts
  identical to the arm-numbered one (this fails against the old code), that
  `iter_process_pvar_positions` reads named chroms, and that popdep rejects a merged
  pvar.

Validation: `ruff check` on the four touched sources reports the same 11 pre-existing
errors as the unmodified `HEAD` versions (unused imports and `E701` in `popdep.py` /
`ref_v1.py`) — no new findings, though note CI runs `ruff check src/python tests` and
would flag those pre-existing ones. Full suite `214 passed` in 118s, excluding the
known-hanging `tests/test_mapq_bin_popdep.py`.

## 2026-09-03 — Rare-variant gene burden implemented

`wap_burden_test` had been a declared stub that exited 1. It now runs.

New `src/python/genetics/gwas/burden.py` plus `tests/test_burden.py` (14 tests).
The stub listed four open design questions; they are settled as: group by the VEP
`Gene` column of `{id}.variant_sets.tsv` (the `*.extract` lists carry IDs only);
no homoeolog triad collapsing, since A/B/D are separate pfiles and no triad map is
wired in; collapse by minor-allele `count` (default) or `carrier` indicator via
`--assoc_wap_burden_collapse`; no frequency weighting, which would be a no-op at
the aggregation factor these sets actually have.

Mechanics: plink2 applies `assoc.keep` and the set's `*.extract` and writes an
additive matrix, then Python collapses per gene and regresses. plink2 has no
gene-collapsing test, so the regression is Python — covariates are projected out
once by QR and each gene is then a simple regression on the residuals
(Frisch-Waugh-Lovell). `test_burden_beta_and_p_match_statsmodels_ols` pins beta,
se and p to a full statsmodels OLS fit at 1e-9 relative.

Wiring changes beyond the process body:

- The burden branch now shares the structure-PC block with the single-variant
  branch. The stub took no covariates at all.
- pfile and set travel as one flat tuple. The first draft passed two channels
  derived from the same source, which Nextflow zips by arrival order — that risks
  pairing a subgenome with another subgenome's extract list.
- The branch fans out per subgenome, resolving `{id}.{set}.extract` and
  `{id}.variant_sets.tsv`, and skips a subgenome whose extract is missing or empty
  (`plink2 --extract` fails outright on an empty list; several sets are legitimately
  empty for a given subgenome).
- New params `assoc_wap_burden_sets_dir` and `assoc_wap_burden_collapse`;
  `assoc_wap_burden_set` is now required and drives discovery, with
  `assoc_wap_burden_extract` demoted to a single-file override.

### Silent wrong result caught in the first run

`68run_wap_ph_burden` exited 0 and produced plausible-looking output that was
entirely wrong: mean 195 carriers per gene out of 2000 samples, i.e. MAF ≈ 0.05 for
a set defined as MAF < 0.01. Cross-checking the claimed `MAF_wap` against frequencies
recomputed from the `.raw` gave a correlation of 0.9999 (median MAF 0.0008), so the
annotation was right and the bug was mine.

Cause: `collapse_gene_scores` zero-filled missing calls *before* flipping the counted
allele. All 292 pLoF variants in subgenome A have ALT as the major allele, so every
column is flipped; a missing call filled to 0 then became `2 - 0 = 2`, a homozygous
carrier of the rare allele. With a 9.8% mean missing rate that produced 194 fake
carriers per variant against 4.6 real ones.

Fix: compute the frequency with missing skipped, flip, and only then zero-fill, so
`2 - NaN` stays missing. Added `test_missing_call_on_a_flipped_variant_is_not_a_carrier`
built to the real data's shape (ALT major, 10% missing), which fails on the old order.
Also added a per-gene `mean_missing_rate` column, since missing-as-non-carrier biases
a poorly called gene toward the null and that should be visible in the table.

`69run_wap_ph_burden_fix` reran clean. Carrier counts now match the annotated MAF
(mean 4.2–4.6 of 2000) and the p<0.05 count fell from 40 to 23 in A against a null
expectation of 14.5. No gene passes Bonferroni in any subgenome — the strongest is
`TraesCS1A02G064000` in A at p = 2.1e-4 with 13 carriers, against a 1.7e-4 threshold.

### The aggregation factor makes this run scientifically thin

Worth recording plainly: on these sets burden buys almost nothing. `plof_rare_wap`
holds 292 variants across 289 genes in subgenome A — **1.01 variants per gene**, with
286 genes holding exactly one. Collapsing one variant is a single-variant test.
Widening to `protein_altering_rare_both` only reaches 1.34 (7139 of 9675 genes still
hold one).

The cause is the coding yield, not the rarity threshold: of 3.03M variants in A,
86.8% are already `rare_wap`, but only 6.9% carry a VEP gene and 99.5% fall in the
`other` coding mask (plof_high 328, protein_altering 14174). The machinery is correct
and will aggregate properly on a denser callset; the current numbers should not be
read as a rare-variant result.
